# Git: шпаргалка

## 1. Репозиторий

| Команда / понятие | Что делает |
|---|---|
| `git init` | Создаёт новый пустой репозиторий в текущей папке |
| `git clone <url>` | Копирует существующий репозиторий со всей историей и сам настраивает `origin` |
| `git status` | Показывает, какие файлы изменены и в какой они области |
| папка `.git` | Здесь Git хранит всю историю. Удалить её — потерять историю, файлы останутся |

Git **распределённый**: у каждого полная копия истории, поэтому почти всё работает без интернета.

---

## 2. Три области и коммит

```
Working Directory  ──git add──▶  Staging  ──git commit──▶  Repository
```

| Команда / понятие | Что делает |
|---|---|
| `git add <файл>` | Кладёт изменения файла в staging |
| `git commit -m "..."` | Сохраняет содержимое staging в историю как новый коммит |
| `git config --global user.name / user.email` | Кто ты: подписывается в каждом коммите. Нужно один раз |
| untracked | Новый файл, Git за ним ещё не следит |
| modified | Файл уже есть в истории, но изменён |
| staged | Изменения отобраны и войдут в следующий коммит |

**Зачем staging:** чтобы разбивать работу на логические коммиты (баг-фикс отдельно, README отдельно).

## 3. Смотрим историю и изменения

| Команда | Что делает |
|---|---|
| `git log --oneline` | История коммитов, одна строка на коммит, новые сверху |
| `git log --oneline --graph --all` | История всех веток в виде дерева |
| `git log --stat` / `git log -p` | Какие файлы менялись / что именно менялось в каждом коммите |
| `git show <хеш>` | Один коммит целиком: автор, сообщение, изменения |
| `git diff` | Изменения, ещё **не** добавленные в staging |
| `git diff --staged` | Изменения в staging: то, что войдёт в коммит |
| `git restore --staged <файл>` | Убрать файл из staging, изменения остаются в файле |
| `git restore <файл>` | ⚠️ Выбросить изменения в файле, вернуть версию из коммита. Безвозвратно |

**status vs diff:** status — *какие* файлы изменены; diff — *что именно* в них изменилось.
`q` — выйти из просмотра длинного вывода.

## 4. Что внутри коммита

| Понятие / команда | Что это |
|---|---|
| snapshot | Коммит хранит снимок всего проекта, а не список изменений |
| blob | Содержимое одного файла (без имени), со своим хешем |
| tree | Список имён файлов и подпапок со ссылками на их хеши, то есть снимок папки |
| commit | tree + parent + автор + время + сообщение |
| хеш | SHA-1, вычисляется из содержимого коммита. Любое изменение — новый хеш |
| parent | Хеш предыдущего коммита. Так коммиты связываются в историю. У первого коммита parent нет |
| `HEAD~1`, `HEAD~2` | На один / два коммита назад от текущего |
| `git commit --amend` | Заменить последний коммит новым (сообщение и/или файлы). Новый хеш |
| `git commit --amend --no-edit` | То же, но сообщение оставить прежним |

- Неизменённые файлы не копируются: новый tree ссылается на старые blob. Плюс сжатие и упаковка.
- Изменил коммит в середине истории — меняются хеши его и **всех** следующих.
- Большие данные (CSV, Parquet) не коммитят: они плохо сжимаются и остаются в `.git` навсегда.

## 5. Ветки и HEAD

| Команда / понятие | Что делает |
|---|---|
| ветка | Указатель (файл с хешем) на один коммит. Поэтому ничего не стоит |
| HEAD | Указатель на текущую ветку (HEAD → ветка → коммит) |
| `git branch` | Список веток, текущая отмечена `*` |
| `git switch -c <имя>` | Создать ветку на текущем коммите и перейти на неё |
| `git switch <имя>` | Перейти на ветку: HEAD переключается, файлы меняются на её снимок |
| `git branch -d <имя>` | Удалить ветку (только указатель, коммиты остаются) |
| detached HEAD | HEAD указывает прямо на коммит, без ветки. Новые коммиты легко потерять |
| `git reflog` | Журнал всех мест, где был HEAD. Спасает «потерянные» коммиты |

- При коммите сдвигается **ветка**, на которую указывает HEAD. Сам HEAD остаётся на ветке.
- `checkout` — старая команда, которая делала всё. Её разделили на `switch` (ветки) и `restore` (файлы).

## 6. Слияние и конфликты

| Команда / понятие | Что делает |
|---|---|
| `git merge <ветка>` | Вливает указанную ветку в текущую. Сначала встать на ветку, *куда* вливаем |
| fast-forward | В целевой ветке нет новых коммитов — указатель просто сдвигается вперёд |
| merge commit | Обе ветки ушли вперёд — создаётся коммит с двумя родителями |
| конфликт | Обе ветки изменили одни и те же строки (или одна удалила файл, другая изменила) |
| маркеры | Между `<<<<<<< HEAD` и `=======` — текущая ветка, между `=======` и `>>>>>>>` — вливаемая |
| `git merge --abort` | Отменить merge, вернуть всё как было |

Шаги решения конфликта:
1. `git status` — найти файлы с конфликтом
2. Отредактировать файл, удалить маркеры
3. `git add <файл>` — конфликт решён
4. `git commit --no-edit` — завершить merge

Vim открылся случайно: `Esc` → `:wq` → Enter.

## 7. Работа с GitHub

| Команда / понятие | Что делает |
|---|---|
| Git vs GitHub | Git — программа контроля версий локально. GitHub — сервис для хранения репозиториев и командной работы (PR, review, CI) |
| `origin` | Имя ссылки на удалённый репозиторий |
| `origin/main` | Локальная метка: где была `main` на GitHub при последней связи. Двигается при fetch/pull/push |
| `git remote -v` | Показать настроенные remote |
| `git remote add origin <url>` | Привязать локальный репозиторий к удалённому |
| `git push -u origin <ветка>` | Отправить ветку. `-u` связывает её с `origin/<ветка>`, дальше хватит `git push` |
| `git fetch` | Скачать новое и сдвинуть `origin/main`. Твои ветки и файлы не меняются |
| `git pull` | `fetch` + `merge`: скачать и сразу влить |
| `git log main..origin/main` | Какие коммиты придут при pull |
| `git diff main...origin/main --stat` | Какие файлы изменились у них с момента расхождения |
| `git fetch --prune` | Удалить метки `origin/...` веток, удалённых на GitHub |

- Push отклонён (`rejected`): на GitHub есть коммиты, которых нет у тебя → `git pull` → решить конфликты → `git push`.
- Никогда `git push --force` в общую ветку.

Feature branch workflow:
1. `git switch main && git pull`
2. `git switch -c <задача>`
3. Коммиты
4. `git push -u origin <задача>`
5. Pull request → code review → merge на GitHub, удалить ветку
6. `git switch main && git pull && git branch -d <задача>`

| Понятие / команда | Что это |
|---|---|
| pull request | Запрос на GitHub влить ветку в `main`. В GitLab — merge request |
| code review | Коллеги проверяют код до `main`: ловят ошибки, делятся знаниями, держат единый стиль |
| `.gitignore` | Список того, что Git не отслеживает |
| что кладём в `.gitignore` | `.env` (секреты), `data/`, `*.csv`, `*.parquet`, `__pycache__/`, `.venv/`, `.vscode/`, `.idea/` |
| `git rm --cached <файл>` | Перестать отслеживать уже закоммиченный файл, оставив его на диске |

- `.gitignore` не действует на уже отслеживаемые файлы — нужен `git rm --cached`.
- Пароль попал на GitHub: **сначала сменить пароль**, потом убирать из репозитория.

## 8. Отложить, перенести, отменить

| Команда | Что делает |
|---|---|
| `git stash` / `git stash -u` | Отложить незакоммиченные изменения / включая новые файлы |
| `git stash list` | Что лежит на полке |
| `git stash pop` | Вернуть последние отложенные и убрать с полки |
| `git stash apply` | Вернуть, но оставить копию на полке |
| `git cherry-pick <хеш>` | Скопировать изменения одного коммита в текущую ветку новым коммитом (новый parent — новый хеш) |
| `git revert <хеш>` | Создать новый коммит, отменяющий указанный. История не переписывается |
| `git reset --soft HEAD~1` | Сдвинуть ветку назад, изменения остаются в staging |
| `git reset --mixed HEAD~1` | Сдвинуть ветку назад, изменения остаются в файлах, но не в staging (по умолчанию) |
| `git reset --hard HEAD~1` | ⚠️ Сдвинуть ветку назад и стереть изменения. Коммиты можно найти через reflog |

- Аргумент **reset** — *куда* поставить ветку. Аргумент **revert** — *какой* коммит отменить.
- Запушенное отменяем через **revert**. **reset** — только для локальных коммитов.

## 9. Rebase

| Команда / понятие | Что делает |
|---|---|
| `git rebase main` | Переносит коммиты текущей ветки поверх `main`, как будто работа началась после её последнего коммита |
| `git rebase --continue` / `--abort` | Продолжить после решения конфликта / отменить rebase |
| `git pull --rebase` | `fetch` + `rebase` вместо merge: без лишних merge-коммитов |
| `git push --force-with-lease` | Отправить переписанную историю своей ветки. Откажет, если кто-то успел запушить |
| `git rebase -i HEAD~3` | Переписать последние 3 коммита. В списке старые сверху |
| `pick` / `reword` / `edit` | Оставить / изменить сообщение / остановиться и изменить файлы |
| `squash` vs `fixup` | Оба склеивают с предыдущим коммитом. squash объединяет сообщения, fixup выбрасывает своё |
| `drop` | Удалить коммит |

Rebase под капотом = cherry-pick каждого коммита поверх новой основы + сдвиг указателя ветки. У всех перенесённых коммитов новые хеши.

**Золотое правило:** не делать rebase коммитов, которые уже запушены и которыми пользуются другие. Хеши меняются, и истории расходятся.

| | Merge | Rebase |
|---|---|---|
| Что делает | Соединяет ветки merge-коммитом | Переносит коммиты на новую основу |
| История | Честная, с ветвлениями | Прямая, линейная |
| Когда использовать | Влить готовую ветку в `main`, общие ветки | Обновить свою ветку от свежей `main` перед PR |

## Мои правила работы с Git

1. Перед каждым коммитом: `git status` → `git diff` → `git diff --staged`.
2. Один коммит — одно логическое изменение, с понятным сообщением.
3. Не коммитить секреты и большие данные. `.gitignore` создаётся сразу.
4. Не пушить напрямую в `main`: ветка → pull request → review → merge.
5. Не переписывать (amend, reset, rebase) то, что уже запушено в общие ветки. Для отмены — `revert`.
